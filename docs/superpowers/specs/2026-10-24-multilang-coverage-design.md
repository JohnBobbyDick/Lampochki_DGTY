## Зачем

Java Blueprints — визуализатор и анализатор Java-кода (редактор ↔ граф, дефекты, Big O, правка через граф,
запуск, сравнение выводов, декомпозиция, ИИ-советы). Пользователь хочет:

1. чтобы панель «Дефекты» всегда отражала текущий код, а ИИ показывал только применимые правки;
2. честное сравнение выводов «предыдущий запуск ↔ текущий» для каждого файла отдельно;
3. скачивать изменённые файлы;
4. видеть, насколько ускорит код предложенная ИИ правка (Big O «сейчас → после»);
5. анализ покрытия кода в духе инструмента JavaScope;
6. полноценную поддержку Stream API / Collectors;
7. те же возможности для Python и C++.

Сроков нет, делаем сейчас. **[решение пользователя]** Порядок: дефекты → сравнение → выгрузка → покрытие →
сложность → стримы → Python → C++. (Покрытие заняло место «подсветки изменений», от которой пользователь
отказался.) Каждый этап — отдельный законченный кусок, который можно проверить и закоммитить.

## Антицели (что сделает работу провалом, даже если «технически работает»)

- В панели остаются дефекты/советы/ошибки про уже исправленный код.

- Регрессии Java-функциональности (все существующие тесты должны проходить).

## 1. Дефекты всегда актуальны + ИИ-исправление синтаксиса

**[решение пользователя]** После правки кода из панели «Дефекты» должно исчезать всё, что пользователь
изменил/устранил: дефекты анализа, ИИ-советы и ошибки (синтаксис/компиляция). Конкретного воспроизведения
пользователь не дал — причину нужно найти самостоятельно (воспроизвести на примерах из `test_monoliths/`).

Наблюдения из кода (кандидаты в причины, не проверены):
- `aiReview` (панель «✨ N идей») и `ai` (ответ «Объяснить с ИИ») живут в store до следующего ответа ИИ
  и не сбрасываются при правке кода — советы про старый код висят минимум 5 с + время ответа модели,
  а при выключенном ИИ/ошибке — бесконечно.
- `useSync` при неуспешном `/parse` выходит, не вызывая `/analyze`: старые `defects`/`bigo` остаются.
- При синтаксической ошибке `parse_java` делает `_best_effort_parse` — дефекты считаются по частичному AST,
  возможны «призраки».

Требования:
- Любой результат анализа привязан к версии кода, по которой он посчитан. При изменении кода всё, что
  относится к старой версии, либо пересчитывается, либо убирается. Совет ИИ, чей `old_code` больше не
  находится в текущем коде (`patcher.locate`), скрывается сразу, не дожидаясь нового ревью.
  **[моё решение]** Советы, чей фрагмент всё ещё на месте, остаются видимыми до прихода нового ревью
  (чтобы панель не мигала на каждой букве).
- Ошибки компиляции (`javac` и аналоги для новых языков) показываются в разделе «Синтаксис / Компиляция»
  наряду с ошибками парсера. **[моё решение]** Компиляционная проверка запускается в том же debounce-цикле,
  что и анализ (`check_compiles` уже есть в `core/runner.py`), с отменой устаревших запросов.
- **[решение пользователя]** У каждой синтаксической/компиляционной ошибки — кнопка «✨ Исправить с ИИ».
  Новый промпт (`ai/prompts/syntax_fix.txt`) получает код и текст ошибки, возвращает пару
  `old_code → new_code` (как у ревью); `patcher.build_patch` проверяет, что результат компилируется.
  Для патчера «исходный код не компилируется» — нормальная ситуация: проверяем, что **после** правки
  ошибок стало меньше/нет, а не что «до» компилировалось (сейчас `validate` сравнивает с оригиналом —
  нужно учесть).
- **[решение пользователя]** Пользователь видит только то, что можно применить: если правка не
  компилируется, совет не показывается вообще (не «заблокирован с причиной», а скрыт). Это касается
  ревью, «Объяснить с ИИ» и исправления синтаксиса. **[моё решение]** Критерий «можно применить» единый
  для всех трёх сценариев: правка **не добавляет новых ошибок** по сравнению с текущим кодом (а для
  исправления синтаксиса — ещё и устраняет целевую ошибку). Так ревью не пустеет, когда пользователь в
  середине правки и файл временно не компилируется. Если текущий код компилируется, это означает
  «после правки компилируется». **[моё решение]** Советы без правки кода (чистый текст)
  в авто-ревью тоже скрываются; в «Объяснить с ИИ» текстовое объяснение остаётся, но без блока с кодом,
  если правка невалидна. Если после фильтрации ничего не осталось — «ИИ не нашёл применимых правок».
  **[моё решение]** Сервер делает до 2 повторных запросов к модели, если ни одна правка не прошла проверку,
  передавая ей ошибки компиляции предыдущей попытки.

## 2. Сравнение выводов — по каждому файлу, с предыдущим запуском

**[решение пользователя]** Пример:

```
Запуск demo.java          → 12
Запуск calc.java          → 7
Запуск изменённого demo   → 25   Сравнение demo.java: старый 12, новый 25
Запуск изменённого calc   → 12   Сравнение calc.java: старый 7,  новый 12
```

- «Старый» вывод — **предыдущий запуск этого же файла** (не исходник и не первый запуск).
- Каждый Run, дошедший до выполнения (интерактивная консоль `/api/ws/run`), записывается в историю
  **этого файла** — **[моё решение]** включая ненулевой код выхода, необработанное исключение, таймаут и
  остановку по Stop (с пометкой статуса в панели: «было 12 → теперь исключение» — важный случай для
  сравнения); ошибки компиляции в историю не попадают. Запись идёт (`ProjectFile` в `useProject`, по `id`): stdout, stderr, exit code, длительность,
  введённый stdin, хеш/текст кода. **[моё решение]** Храним последние 2 запуска на файл (больше не нужно
  для «старый/новый»), в памяти вкладки, без localStorage.
- Панель сравнения показывает для активного файла: предыдущий vs последний запуск, diff stdout как сейчас,
  плюс подпись «стдин был разный», если ввод отличался. Переключение файла переключает сравнение;
  выводы разных файлов никогда не смешиваются.
- Если у файла меньше двух запусков — пустое состояние «Запустите файл ещё раз после правки, чтобы
  сравнить выводы».
- Кнопка Compare больше не перезапускает оригинал: сравнение строится из записанных запусков. **[моё
  решение]** Quality Gate (`/quality-gate`, `/decompose/verify`) и «Проверить поведение» у ИИ-правки
  продолжают сравнивать с исходником/до-правки, как сейчас — это отдельная проверка эквивалентности.
- `loadDocument` больше не должен терять историю запусков файла при переключении вкладок.

## 3. Выгрузка

**[решение пользователя]** Оба варианта:
- «Скачать» у активного файла (в шапке/вкладке файла) — текущий текст под исходным именем файла.
- «Скачать изменённые» — zip только с изменёнными файлами (`code !== original`), с сохранением папок.
  Кнопка неактивна, если изменённых нет.
- **[моё решение]** Zip собирается на сервере новым эндпоинтом (переиспользуя код `/decompose/zip`), чтобы

## 4. Покрытие кода (аналог JavaScope)

JavaScope — инструмент покрытия: отслеживает, какие части кода выполнились во время работы программы.
**[решение пользователя]**
- Метрики: **все четыре** + строки:
  - покрытие строк (выполнялась ли строка, сколько раз);
  - покрытие методов (вызывался ли метод/функция);
  - покрытие ветвлений (каждая ветка `if`/`else`, `switch`-case, тело цикла выполнялось / пропускалось,
    `?:`, `catch`);
  - логическое покрытие (каждое элементарное условие внутри `&&`/`||`/`!` принимало и `true`, и `false`);
  - реляционное покрытие (для каждого сравнения `a < b`, `<=`, `>`, `>=`, `==`, `!=` — встречались ли
    случаи `a < b`, `a == b`, `a > b`; цель — проверка граничных значений).
- Где показывать: **в редакторе** (метки строк в gutter: зелёная — выполнена, красная — не выполнена,
  жёлтая — частично, т.е. есть непройденная ветка/условие; счётчик выполнений при наведении) и **панель
  «Покрытие»** внизу: проценты по каждой метрике для файла и по методам, список непройденных
  веток/условий/граничных случаев с переходом к строке.
- Языки: **Java, Python, C++** (для новых языков — когда они появятся в этапах 7–8). JavaCC — нет.

Поведение:
- Покрытие собирается при обычном Run в интерактивной консоли (ввод `Scanner` работает как раньше) —
  **[моё решение]** всегда, без отдельного режима; если инструментирование не удалось (неподдерживаемая
  конструкция), программа запускается без покрытия, а в панели — причина.
- **[решение пользователя]** Покрытие **накапливается**: все запуски одного и того же текста кода (по хешу,
  для каждого файла отдельно) суммируются — так логическое и реляционное покрытие можно «добрать» запусками
  с разным вводом. Правка кода сбрасывает накопление; в панели есть кнопка «Сбросить покрытие» и счётчик
  «запусков учтено: N». **[моё решение]** После правки метки в редакторе исчезают, панель показывает
  «Код изменён — покрытие сброшено, запустите снова». Если вернуть код к прежнему тексту (Ctrl+Z),
  накопление не восстанавливается — сброс окончательный. В покрытие идут все запуски, которые дошли до
  выполнения (включая исключение, ненулевой код выхода, таймаут, Stop) — записывается всё, что успело
  выполниться.
- Вывод программы не должен меняться из-за инструментирования (данные покрытия идут отдельным каналом —
  файл в temp-каталоге запуска или отдельный дескриптор, не stdout/stderr пользователя).
- Таймаут 10 с и лимит памяти сохраняются; накладные расходы инструментирования не должны съедать
  бюджет на типичных примерах.

Способ — на усмотрение исполнителя, с ограничением: нужны логическое и реляционное покрытие, которые
байткодные агенты (JaCoCo) не дают, поэтому ожидаемый путь — **инструментирование исходника** по AST
(вставка вызовов счётчика в начало методов/веток, обёртки условий и сравнений), с сохранением номеров строк
(для gutter). Для Python допустим `sys.settrace`/`sys.monitoring` для строк + AST-трансформация для
условий. Детали (вспомогательный класс-счётчик, перегрузки для типов операндов сравнения, формат данных) —
решает исполнитель.

## 5. Сложность «сейчас → после ИИ» и ожидаемое ускорение

**[решение пользователя]**
- Показывается в существующей строке списка «Сложность методов · Big O» (вида «Demo.main · линейная ·
  O(n)») в `DiagnosticsPanel`: текущая сложность и сложность после предложенных ИИ правок, например
  `O(n²) → O(n) · ~1000× быстрее`. Видно **до** нажатия «Применить».
- Ускорение — **ожидаемый прирост по формуле**, без запуска.

Детали:
- Для каждого применимого ИИ-патча сервер считает Big O методов на пропатченном коде (`analyze_ast` по
  результату `replace_range`) и отдаёт в патче `bigo_before`/`bigo_after` для затронутых методов.
- «После ИИ» в строке метода = сложность, если применить все текущие применимые советы, затрагивающие этот
  метод. **[моё решение]** Если советов несколько и они не конфликтуют — применяем последовательно и
  считаем по итоговому коду; если конфликтуют — берём лучший одиночный.
- Ускорение: отношение `f_before(n) / f_after(n)` при **[моё решение]** n = 1000 (подпись «при n ≈ 1000»
  в тултипе), округлённое до «красивого» числа (~2×, ~5×, ~10×, ~100×, ~1000×). Для O(n)→O(n) и т.п.
  («та же сложность») ускорение не показывается. Если стало хуже — показываем красным без «быстрее».
- Тот же бейдж «было → станет» — в карточке ИИ-совета рядом с diff. **[моё решение]**

## 6. Stream API и Collectors (Java)

**[решение пользователя]** Все четыре:
- **Узлы на графе:** цепочка `source.stream().filter(..).map(..).collect(Collectors.toList())` в CFG
  отображается конвейером: узел-источник → узел на каждую операцию (`filter`, `map`, `flatMap`,
  `sorted`, `distinct`, `limit`, `reduce`, `forEach`, `collect(Collectors.groupingBy/joining/toMap/…)`).
  Лямбда операции — текст узла. Новый вид узла в `GraphCanvas/nodes/kinds.ts`.
- **Правка через граф:** двойной клик по узлу операции → правка текста (`x -> x > 0` → `x -> x >= 0`,
  `map` → другой лямбдой) → код перегенерируется. Требует стабильных id узлов стрима (как `n0…` у CFG)
  и поддержки в `code_generator`.
- **Big O:** проход по стриму — O(n); `sorted` — O(n log n); `distinct`/`groupingBy` — O(n) (хеш);
  вложенный стрим/стрим внутри цикла — умножение; `limit`/`findFirst`/`anyMatch` — без понижения оценки
  (худший случай). `bigo_analyzer` уже грубо учитывает `.stream(` regex-ом — заменить на разбор цепочки.
- **Дефекты и советы:** статические правила, например: стрим, создаваемый в цикле по той же коллекции;
  `collect(toList()).size()` вместо `count()`; `filter(..).findFirst().isPresent()` вместо `anyMatch`;
  `sorted()` перед `findFirst()` вместо `min`; `forEach` с изменением внешней коллекции; «цикл можно
  заменить стримом» (подсказка). Точный список правил — исполнитель, 5–8 правил достаточно.

Парсер — `javalang` (Java ≤ 8): лямбды и ссылки на методы уже разбираются (`core/parser.py`), records и
switch-выражения — нет, это ограничение сохраняется.

## 7–8. Python и C++

**[решение пользователя]**
- Язык определяется **по расширению файла**: `.java`, `.py`, `.cpp`. **[моё решение]** Также `.cc`,
  `.cxx`, `.hpp`, `.h` → C++.
- Возможности — **всё как у Java**: подсветка в редакторе (режим Ace), CFG / граф вызовов / диаграмма
  классов, дефекты, Big O, правка через граф с перегенерацией кода, запуск с интерактивной консолью,
  сравнение выводов, покрытие, декомпозиция с Quality Gate, ИИ-советы/ревью/исправление синтаксиса
  (промпты под язык: «опытный Python/C++-ревьюер», правильный блок кода, `imports` → `import`/`#include`).
- Версии: **Python 3.11+, C++17** (`g++ -std=c++17`).
- Зависимости разрешены: **[моё решение]** Python разбирается встроенным `ast`; C++ — `tree-sitter` +
  `tree-sitter-cpp` (pip). `g++` и `python3` добавляются в backend-образ и в `sandbox/Dockerfile`.
- Декомпозиция: выносятся **свободные функции и классы**: Python → модули `.py` с `import`; C++ →
  пары `.h`/`.cpp` с `#include` и include-guard/`#pragma once`. Quality Gate компилирует/запускает
  получившийся набор файлов и сравнивает вывод.
- Демо-примеры: аналоги `test_monoliths/*.java` на Python и C++ с теми же типами дефектов — и на экране
  приветствия, и для тестов.
- Запуск: Python — `python3 main.py` (точка входа — файл целиком / `if __name__ == "__main__"`); C++ —
  компиляция `g++` + запуск бинаря; таймаут/память как у Java, docker-режим тоже.

Архитектура **[моё решение]**: бэкенд получает слой языков (`core/lang/` или аналог) с общим интерфейсом
(парсер → тот же нормализованный JSON-AST, что у Java: классы/функции/операторы со спанами; генератор
кода; раннер; правила декомпозиции; инструментирование покрытия). Межъязыковые части (`cfg_builder`,
`bigo_analyzer`, `call_graph`, `class_diagram`, общая часть `defect_detector`) работают по
нормализованному AST. Для Python/C++ свободные функции модуля представляются в AST псевдоклассом модуля
(чтобы ссылки вида `Module.func` работали как `Class.method`). Все запросы, принимающие код, получают
поле `language`; `state.SESSION` хранит язык. Существующие Java-ответы API не меняются по форме.
Конкретные дефект-правила для Python/C++ — на усмотрение исполнителя (аналоги Java-правил: конкатенация
строк в цикле, вложенные циклы по одной коллекции, поиск в списке в цикле, пустой except/catch, и т.п.).

**[решение пользователя]** Аналог стримов для новых языков — **только Big O и дефекты**: Python —
comprehensions, генераторные выражения, `map`/`filter`/`sorted`/`sum`/`any`; C++ — `<algorithm>`
(`std::sort`, `std::find`, `std::count_if`, `std::accumulate` и т.п.). На графе это обычный узел
оператора (без конвейера и без отдельной правки шагов).

**[решение пользователя]** Модель «один файл = одна программа» сохраняется для всех языков: Run/анализ
работают с одним файлом; `#include` локальных заголовков и `import` соседних файлов проекта не
поддерживаются (стандартная библиотека — да). Результат декомпозиции (несколько файлов) проверяется
Quality Gate и скачивается zip-архивом, как у Java. Отдельный `.h`-файл можно открыть и анализировать,
но не запускать (кнопка Run неактивна с подсказкой).

**[моё решение]** Граница «готово» для Python и C++ — какие конструкции обязаны иметь полноценные узлы
CFG, правку через граф и покрытие ветвлений/условий:
- Python: `if/elif/else`, `for`/`while` (включая `else`), `break`/`continue`, `return`, `try/except/
  else/finally`, `raise`, `with`, `match` (как цепочка веток), присваивания/вызовы; функции, методы
  классов, `@staticmethod`/`@classmethod`, вложенные функции — как обычные функции.
- C++: `if/else`, `for`, range-`for`, `while`, `do-while`, `switch`, `break`/`continue`, `return`,
  `try/catch`, `throw`; свободные функции, классы/структуры с методами (в т.ч. определёнными вне класса
  `A::f`), конструкторы, `namespace`.
- Всё прочее (лямбды, comprehension, `yield`, `async`, декораторы с логикой, шаблоны, макросы,
  перегрузка операторов, `goto`) — один узел-оператор с исходным текстом: показывается, анализируется
  для Big O по мере возможности, правится как текст целиком; покрытие — на уровне строки. Это не
  считается «урезанной поддержкой». Шаблонные функции/классы разбираются и показываются как обычные.
- Обязательное покрытие: всё, что встречается в новых демо-примерах, плюс список выше.

Python и C++ — два отдельных этапа (сначала Python, потом C++), каждый проходит весь список возможностей.

## Ограничения и инварианты

- UI и сообщения — на русском; визуальный стиль — по `DESIGN.md`.
- Сервер остаётся однопользовательским (глобальный `SESSION`).
- Детерминированные id узлов CFG — основа правки через граф; для стримов и новых языков то же требование.
- Ключи/прокси ИИ не попадают в ответы и логи (существующее правило `llm_client`).
- Тесты бэкенда (`python -m pytest` в `backend/`) проходят на каждом этапе; новые возможности покрываются
  тестами на `test_monoliths/` и новых примерах. Фронтенд проверяется `npm run build`.

## Оставлено исполнителю

Конкретные компоненты, формат данных покрытия, вид бейджей и меток (в рамках `DESIGN.md`), формулировки
промптов, список дефект-правил для стримов и новых языков, структура слоя языков, разбиение этапов на
коммиты.
